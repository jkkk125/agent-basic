# 学习记录（历史）

2026-11-18 及之前的探索和拆分记录，按时间倒序，不再追加。之后的改动记在根目录的 `CHANGELOG.md`。

### 2026-11-18 按职责拆分模块

**问题**：功能都堆在 `main.ts` 和 `tools.ts` 里，继续加功能时有四处互相缠绕：

- 加一个工具要改三处（定义、`initTools` 列表、`EXEC_TOOL` 分支），`apply_patch` 的执行和联网工具的计次还另外写在 `main.ts` 里。
- `ask()` 同时负责循环控制、终端打印和 usage 记账，真正的循环逻辑被 90 行打印淹没。
- “库里存的”变成“发给模型的”只有一行 `[...history, ...items]`，没有独立的落点。
- client、系统提示、MCP 连接都是模块级全局变量，没法用另一套配置再跑一个循环。

**拆分结果**（都在 `src/` 下）：

- `main.ts`：入口，创建依赖并运行 REPL。
- `loop.ts`：`ask()` 循环，依赖全部由参数传入，不打印、不落库。
- `context.ts`：`buildInput()`，由完整记录派生出发给模型的 input。
- `prompt.ts`：组装系统提示。
- `render.ts`：把循环发出的事件打印到终端。
- `session.ts`：读历史、存一轮对话、新建会话、起标题、usage 记账。
- `tools/`：每个工具一个文件，`registry.ts` 汇总并按名分发。

**学到的**：

- 工具的“定义”和“执行”应该放在一起。`zodResponsesFunction` 只用来生成给模型看的定义；它挂的 `$callback` SDK 自己不会调用，执行循环本来就得自己写。function、custom、MCP 三类工具统一成 `AgentTool`（`spec` + `execute`）之后，循环里它们的差别只剩入参格式和回传的 item 类型。
- 循环只说明“发生了什么”（`onEvent`），怎么显示交给监听方。这样循环主体只需要处理 `completed`、`incomplete`、`failed` 三种会改变状态的事件。
- 依赖改为传参之后，循环可以用假 client 测试。把库里一次真实会话回放给新的 `ask()`，产出的 20 条消息和 5 轮 usage 与库里完全一致。
- 工具数组的顺序就是发给模型的顺序，调整它会改变请求前缀、影响 `cached_tokens`。

**行为变化**（其余保持不变）：

1. 工具按模型输出的顺序执行，以前是先执行所有 `apply_patch` 再执行 function 调用。
2. 未知工具名直接返回 `xxx 调用失败: 未知工具`，以前会转发给 MCP。
3. 工具重名时启动报错，以前是本地工具静默优先。

**尚未用真实模型验证**：起标题、流式显示、`--session` 恢复。唯一一次真实运行是在拆完 `tools/` 之后，验证完可以删掉这一条。

**要留意**：

- 上一条记录里计划的“旧工具输出换占位符”，现在的落点是 `context.ts` 的 `buildInput`：`history` 和 `items` 保持完整，只改返回值。
- `input_item_count` 记的是 `history.length + items.length`，假设发出去的就是全部；做了裁剪之后需要重新定义它的含义。
- `incomplete` 时模型已输出的工具调用会被存下来但不会执行，也就没有对应的输出；下一次请求带着它是否会被接口拒绝，还没验证。

### 2026-11-17 上下文管理：先量一下现状

**问题**：`ask()` 每次请求都发送 `[...history, ...items]`，历史只增不减，对话越长每轮 `input_tokens` 越高。

**数据**（来自本地 `data/agent.db`，`agent_usage` 和 `agent_messages` 两张表）：

- 单个会话单轮 `input_tokens` 最高到 50462，一个 16 轮的提交会话就是这样涨上去的。
- `agent_messages` 里 `function_call_output`（工具输出）共 95 条、约 397k 字符，占全部消息的 70% 以上；`reasoning` 约 56k，`message` 约 41k。

**结论**：上下文膨胀的主要来源是工具输出，不是对话文本。所以第一步优先处理工具输出，而不是先做整段历史摘要。

**接下来的计划**（按顺序，做完一步在这里补一条记录）：

1. 旧工具输出替换成占位符，只保留最近几轮的完整内容。
2. 用 `usage.input_tokens` 判断是否接近上限，超过阈值再对更早的历史做摘要。
3. 对比 `agent_usage` 里压缩前后的 `input_tokens` 和 `cached_tokens`，验证效果。

**要留意**：改历史会破坏前缀，影响 `cached_tokens` 命中率，替换时机要想清楚。
